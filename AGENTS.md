## Project

Self-hosted critical CSS generator for WordPress: replaces WP Rocket's paid Remove Unused CSS / QUIC.cloud's metered free tier. Two halves that ship and version independently but always move together in one PR/release:

- `service/` — a Node/Express service that drives a real headless browser (`penthouse-esm` on Puppeteer, called directly) to render each URL and extract above-the-fold CSS for mobile and desktop. Loading the page and its stylesheets is first-party code in four modules, written to replace the `critical` package (removed on purpose, see the compounding rule on the page-loading layer): `page-fetch.js` (the only server-side HTTP for a page and its stylesheets: policy, limits, error codes), `stylesheets.js` (which stylesheets a page has: parse5, pure), `rebase.js` (`url()` rewriting with `postcss-url`, plus the size and work guards) and `critical-css.js` (the failure policy, the budgets, the layout copy penthouse renders, and `generateCriticalCss()`, the one call `server.js` and `service/scripts/check-render.mjs` make). `service/fixtures/parity/` records what `critical@8.0.0` did and `npm test` replays it; its README lists the 53 deliberate differences.
- `wordpress-plugin/wp-critical-css/` — the installable WordPress plugin (REST receiver, inline/defer injection, WP-Cron trigger). Its test/lint tooling lives in the **sibling** `wordpress-plugin/wp-critical-css-tests/` directory, deliberately — that directory is exactly what `publish-plugin.yml` zips verbatim as the shipped plugin, so it must stay free of `composer.json`/`vendor`/tests.

Not distributed via WordPress.org — installed manually from a GitHub Release zip. See `docs/ARCHITECTURE.md` for how the pieces fit together and `docs/SECURITY-CONTROLS.md` for the full threat model.

## Working style

- Solo-maintained; contributions and bug reports welcome, but keep changes small and reviewable.
- Verify before recommending: check the actual current file/config/CI state before proposing a fix, don't assume from a past commit message or a memory of "how this usually works." Several real bugs this project has shipped only surfaced because an agent downloaded and inspected a raw CI artifact (a Clover coverage report, a Docker build log) instead of trusting a green checkmark or a plausible-sounding theory.
- After each step: what changed, how to test, what remains.
- Touch only what the task requires; match existing conventions (tabs for PHP per WPCS, comments that explain *why* not *what*, inline `// NOSONAR <rule> - <reason>` for a deliberately-accepted static-analysis finding).

## Security

- **Never** commit secrets, tokens, API keys, or real credentials. `.env.example` documents required configuration; `SHARED_SECRET`/`WPCC_SHARED_SECRET` values in examples/tests are always obvious placeholders.
- `SHARED_SECRET` gates the `/generate` and `/sweep` HTTP endpoints; `WPCC_SHARED_SECRET` (same value) gates the plugin's REST receiver. Comparisons are constant-time (`isValidSecret()` in `service/lib.js`) — never introduce a plain `===`/`!==` on a secret.
- This service renders arbitrary URLs with a real headless browser — SSRF is the primary threat model, not an afterthought. Any new network call the service makes (sitemap fetch, a future outbound request) needs to go through `safeFetch()`/`isPrivateOrReservedTarget()` in `service/lib.js` (a page or a stylesheet: only `service/page-fetch.js`, see the compounding rule below), the same private/reserved-address policy already applied to the page fetch and Chromium's own request interception. A gap here has already shipped once (unprotected sitemap fetching, fixed in v0.2.2) — don't reintroduce a fourth, unguarded network path.
- Every GitHub Actions `uses:` must be pinned to a full commit SHA with a `# vX.Y.Z` comment, never a mutable tag. `permissions:` stays minimal per workflow/job: the top level is read-only (`contents: read`) and a job that writes declares its own writes - a top-level write is an OpenSSF Scorecard Token-Permissions finding and every job added later would inherit it.
- Add the `security` label on PRs touching auth, secrets, SSRF protections, or rate limiting.

## Tests

```bash
cd service && npm ci && npm test
```

```bash
cd wordpress-plugin/wp-critical-css-tests && composer install && vendor/bin/phpunit   # needs a local MySQL/MariaDB - see tests/php/wp-tests-config.php
cd wordpress-plugin/wp-critical-css-tests && composer install && vendor/bin/phpcs     # lints both this directory and ../wp-critical-css/
```

`service/lib.property.test.js` (fast-check) runs inside `npm test` with a fixed seed, so a required check can't turn red on a fresh random draw. Explore with `cd service && FC_SEED=random FC_NUM_RUNS=100000 node --test lib.property.test.js`; a failure prints `Property failed after N tests { seed: S, ... }`; replay it with `FC_SEED=S FC_NUM_RUNS=N` (the seed alone only replays the default 300 runs, so a failure found later passes). The weekly `property-fuzz.yml` does the same with far more runs. Keep the file named `*.test.js` (SonarCloud treats it as a test file, so it doesn't count against new-code coverage) and don't rename it to `.mjs`/`.cjs` or move it under a `testdata/` path - OpenSSF Scorecard's fast-check detection only matches `*.js`/`*.jsx` outside those. A Dependabot bump of `fast-check` can change the inputs drawn for the fixed seed: if it turns the property file red, treat that as a finding and replay it as above, not as flakiness.

Don't hand-wave a Docker/Puppeteer change as "should work" — build the image and run the actual smoke test locally when Docker is available (`service/Dockerfile`, or replicate `.github/workflows/ci.yml`'s "Smoke test - real Puppeteer render" step: `service/scripts/check-render.mjs`, which calls the same `generateCriticalCss()` as `server.js`, in mode `url` there and mode `html` offline in `publish-container.yml`). A silent version mismatch between the Dockerfile's base image and `service/package.json`'s own `puppeteer` dependency has broken this exact test in production CI before (v0.2.2) — the two must be bumped together, always.

## Pull requests

Follow [.github/pull_request_template.md](.github/pull_request_template.md) exactly: `Description` · `How to test` · `What stays / known limitations` · `Documentation impact` (tick exactly one: docs updated, or no update needed with a specific reason) · `Checklist`.

Before opening: **milestone**, at least one `type:`/`area:`/`prio:` label, and **assignee `@solarssk`** — set on the PR object itself at creation (`gh pr create --milestone ... --label ... --assignee solarssk`), not added afterward.

Labels: `type: bug` `type: chore` `type: docs` `type: feature` · `area: service` `area: infra` `area: wordpress` (label description still says "wordpress-mu-plugins/" - stale since the mu-plugin→installable-plugin migration in v0.2.1, the path is `wordpress-plugin/` now) · `prio: high` `prio: medium` `prio: low` · `security` `ci`.

**Required status checks** (branch protection): `Build & audit (Node)`, `Docker build smoke test`, `Analyze (javascript-typescript)`, `Semgrep SAST (JS + PHP)`, `SonarCloud scan`, `PHP syntax check (plugin)`. A PR review thread from an automated reviewer (`chatgpt-codex-connector` or similar) must be replied to **and resolved via the GraphQL `resolveReviewThread` mutation** — a plain reply comment does not clear it, and an unresolved thread can leave a PR `BLOCKED` even with every check green.

**Milestone convention:** exactly one milestone is open at a time, named after the *next* version (e.g. `v0.2.2`) — every PR lands there regardless of whether it's a real feature or a one-line CI fix. It stays open, accumulating PRs, until that version actually ships (tag pushed, both publish workflows succeed) — only then does it close. Don't create a new milestone per PR; don't close the open one just because a PR merged into it.

**Dependabot PRs:** `docker` and `npm`/`composer` ecosystems update independently and can't coordinate a single PR across both. When a Dependabot PR breaks CI because of exactly that (the Puppeteer base-image/npm-package mismatch in v0.2.2 is the canonical example — a fix requiring a change *outside* that PR's own diff), don't try to push to the `dependabot/`-owned branch (GitHub blocks non-Dependabot pushes to it) — open a new PR that supersedes it, then close the Dependabot PR with a comment pointing at the replacement. Chrome is pinned separately in `service/Dockerfile` (see the compounding rules): a Dependabot `puppeteer` bump no longer delivers a new Chrome (the pin wins), and a combined puppeteer + base-image supersede PR must also bump (or drop) that pin whenever the new base image ships a Chrome newer than it, or the build fails by design.

## Wiki documentation

`docs/wiki/` is the **only** source of the project's GitHub Wiki: [`publish-wiki.yml`](.github/workflows/publish-wiki.yml) makes the Wiki match it after every merge to `main`, deleting what is no longer there, so never edit the Wiki itself (the next publish overwrites it). The Wiki is the operator-facing documentation (set up, configure, operate, troubleshoot); `docs/*.md` stay the technical reference, and a user-visible change usually touches both. Update the wiki in the same PR as the behaviour it describes.

- The `wiki-docs` job in `ci.yml` (`Wiki docs (sync and links)`) runs on every PR and push. `scripts/check-wiki-docs.mjs` checks the pages (required pages, title = file name, sidebar, every page/heading/repo-file link) **and compares them with the code**: the tables on `docs/wiki/Configuration.md` against the environment variables `service/*.js` reads, the `ENV` values of `service/Dockerfile` (the "Set by the image" table; an image value wins over a code fallback), the `WPCC_*` constants the plugin defines or checks, the routes (`service/server.js` and the plugin's REST route) and their defaults (a default the docs write in code formatting must be verifiable: literal after `||`/`??`, argument, or the `!== 'false'`/`=== 'true'` flag forms); `Getting-Started.md` against the plugin header's `Requires PHP`/`Requires at least`; `Network-Egress-Filtering.md` against the variables in `docker-compose.egress.example.yml`. Adding, removing or re-defaulting any of those without its wiki row fails the job (and a line that touches `process.env` or an Express route in a form the readers do not understand fails it too, instead of being skipped). It is a CI job, not yet a required status check: adding `Wiki docs (sync and links)` to branch protection is the maintainer's call. Run `node scripts/check-wiki-docs.mjs` before pushing, and `node --test "scripts/*.test.mjs"` after touching a checker (no install needed; Node 24).
- The same job reads the PR **description from the API** (not the event payload) and `scripts/check-pr-docs-impact.mjs` compares its `Documentation impact` section with the diff: `Docs updated` needs a documentation file in the change (`docs/`, any `.md`, `readme.txt`, `.env.example`), `No doc update needed` needs a real reason and is refused when `docs/wiki/` changed. After fixing only the description, re-run the failed job; no new commit is needed.
- Page conventions are on the Editing-the-Wiki page (`docs/wiki/Editing-the-Wiki.md`): the file name is the page address and its title, links between pages are extensionless (`[x](Getting-Started)`), repo files are linked by their full `https://github.com/solarssk/wp-critical-css/blob/main/...` address (checked to exist, anchors included). A new page also goes into `_Sidebar.md` and, if mandatory, `REQUIRED_PAGES` in the script.
- `publish-wiki.yml` pushes with `GITHUB_TOKEN` (job-level `contents: write`; no App or secret) and refuses to run from any ref but `main`. The Wiki git remote only exists once its first page has been created in the Wiki tab.

## Changelog and releases

[CHANGELOG.md](CHANGELOG.md) follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). No `[Unreleased]` section convention here (unlike some other projects) — write the version's own `## [X.Y.Z] - YYYY-MM-DD` heading directly as part of the release-prep PR, grouped by `Security`/`Fixed`/`Added`/`Changed`/`Deploy` as relevant. Only user-facing facts belong here — pure CI/repo-governance changes (a new SonarCloud exclusion, a workflow refactor) don't, unless they change what a deployer actually experiences.

**Closing a milestone (cutting a release), in order:**

1. Open a `release/vX.Y.Z` branch/PR titled `release: vX.Y.Z` bumping, together: `service/package.json` (+`package-lock.json`), the plugin's `Version:` header, its `readme.txt` `Stable tag:`, and adding both the `CHANGELOG.md` entry and a curated `.github/release-notes/vX.Y.Z.{title,md}` pair (`release.yml` and both publish workflows fail fast if any of these is missing or out of lockstep — see `docs/DEPLOYMENT.md`'s Releases section for the exact required shape).
2. Get it merged. **That merge is the whole release trigger** — [`release.yml`](.github/workflows/release.yml) fires on the resulting push to `main`, detects the `release: vX.Y.Z` commit, verifies the artifacts above, creates the tag + GitHub Release, dispatches `publish-container.yml` and `publish-plugin.yml` (which publish to GHCR/Docker Hub and build the plugin zip), and closes the matching milestone. No manual tag push, no second confirmation step — merging the release PR itself is the one human action that starts real, externally-visible publishing, so review it with that weight.
3. If `release.yml` fails partway (e.g. a downstream dispatch step), it's safe to just re-push the same commit or re-run the workflow — it doesn't gate on whether the release already exists, so it retries whatever didn't finish without recreating what did.

Do not hand-write a release body that diverges from what's in `.github/release-notes/` — `scripts/release-display-title.sh`, `release.yml`, and both publish workflows all read those files as the single source of truth for the GitHub Release's title/notes.

## Compounding rules

When an agent repeats a mistake in this repo, add a precise rule here (or to `CLAUDE.md` if it's Claude-Code-workflow-specific rather than a fact any agent should know). One line per real gotcha; cut rules that no longer prevent an actual error.

- SonarCloud runs CI-based analysis (`sonar-project.properties` + the `sonarcloud-scan` job in `ci.yml`), not Automatic Analysis — a `// NOSONAR <rule>` comment does nothing for a rule that reports with no anchor line (check via the SonarCloud issues-search API before assuming a NOSONAR comment works: `line: null` means it won't). Use `sonar.issue.ignore.multicriteria` in `sonar-project.properties` instead for those.
- Dependabot PRs get no Sonar analysis, on purpose: `sonarcloud-scan` is skipped by PR author (`pull_request.user.login`), not `github.actor`, so a human "Update branch" can't hand `SONAR_TOKEN` to a Dependabot-authored branch, and a skipped job counts as passing for the required `SonarCloud scan` check. Don't put `SONAR_TOKEN` in the Dependabot secret store (it stays empty in every solarssk repo) and don't require the SonarCloud GitHub App's `SonarCloud Code Analysis` status - it only exists when a token-bearing scan ran, and requiring it blocked every Dependabot PR (drive-scanner-bridge still has that problem). `-Dsonar.qualitygate.wait=true` makes the required job the actual gate. Main is still analysed on push.
- `pcov` (PHP coverage) only instruments files under its own working directory by default — the plugin's test suite runs from `wordpress-plugin/wp-critical-css-tests/`, but the real source it needs to cover lives in the sibling `wordpress-plugin/wp-critical-css/`. `ini-values: pcov.directory=...` has to point at their common parent explicitly, or every line of the real plugin silently reports 0% regardless of what the tests actually exercise.
- `gh workflow run <file> --ref <tag>` only picks which commit's workflow *definition* runs — it does **not** set that workflow's own `inputs.<name>` fields. `publish-container.yml`/`publish-plugin.yml` both resolve their actual publish target from an `inputs.ref` field that defaults to `refs/heads/main`, so a dispatch from `release.yml` needs `-f ref="$TAG"` too, or the dispatched run silently resolves back to main and skips publishing instead of publishing the tag.
- A squash-merged PR's commit subject becomes `<PR title> (#<number>)`, not the bare title — any commit-message pattern match (like `release.yml`'s release-commit detection) needs to tolerate that suffix, or it will never match on this repo's actual merge history.
- A GitHub Actions concurrency `group:` holds at most one running **and** one pending run — a *third* run queueing while one is running and one is already pending **replaces** the pending run rather than queueing behind it, so it never runs at all. A group keyed too broadly (e.g. one shared key for every push to `main`) can silently evict the one run that actually mattered. Key concurrency groups as narrowly as the workflow allows (`release.yml` uses `github.sha` — every push gets its own group, so nothing can evict another).
- `gh workflow run` only *creates* a `workflow_dispatch` event and returns — it doesn't hand back the run it created, and doesn't wait for it. Anything downstream that needs to know whether that dispatched run actually succeeded (like closing a milestone after a publish workflow) has to separately locate the run (poll `gh run list --workflow <file> --json databaseId,createdAt,event`, filtered to `event == "workflow_dispatch"` and `createdAt` at/after the dispatch) and then `gh run watch <id> --exit-status`.
- Milestones are an Issues-API resource, not a Pull-Requests one, even though PRs carry them too — `PATCH .../milestones/{number}` needs `issues: write` on `GITHUB_TOKEN`. An explicit `permissions:` block makes every unlisted scope `none`, so a workflow that only lists e.g. `contents`/`actions` gets a silent 403 the moment it tries to close a milestone.
- The plugin zip signing in `publish-plugin.yml` is deliberately fail-open (zip uploaded first, every new step `continue-on-error` with its own `timeout-minutes`, a `::warning::` "Plugin zip on the Release is UNSIGNED" when it didn't work): a job-level timeout isn't caught by `continue-on-error`, and `release.yml` waits on that run with `gh run watch --exit-status`, so a hard failure after the zip is public would leave the milestone open and tempt a re-dispatch of both publish workflows. Keep it fail-open: the warning and a post-release check are the control - after a release confirm `gh release view vX.Y.Z --json assets --jq '.assets[].name'` lists `wp-critical-css-X.Y.Z.zip.sigstore.json` and run the `cosign verify-blob` command from DEPLOYMENT.md once. Retry an unsigned release with `gh workflow run publish-plugin.yml --ref vX.Y.Z -f ref=vX.Y.Z` (never from `main`: that signs as `@refs/heads/main`), and never pass a semver tag as `-f ref` for a dry run - that republishes the release.
- A page and its stylesheets are fetched by `service/page-fetch.js` and nothing else, and the local policy proxy (`service/ssrf-proxy.js`) is its only route out: never add another HTTP client or a direct `fetch()` for that path, and never hand a page-controlled string to the file system (a stylesheet reference is a URL to fetch, never a file to read; the one file written is `page.html` in a private `mkdtemp` directory removed in a `finally`; postcss runs with `map: false`). The limits (`LIMITS`, `LOAD_LIMITS`, `MAX_REWRITE_WORK`, the markup bounds in `stylesheets.js`) count DECODED bytes. They are NOT a memory guarantee for rendering, and no comment or doc may say a limit is "sized for" the 1 GiB container: they keep realistic pages (the heaviest measured is 515 KiB of html and 1.05 MiB of css) far inside it and fail an oversize page early and cleanly, but measured there (V8 heap limit 560 MiB) 7.9 MiB of dense css exhausts the Node heap and restarts the container, 3.95 MiB does without swap, and a 9 MiB html page crashes Chrome's renderer (`Page crashed!`, service alive); the rendering stage (penthouse and Chrome) is the same code as in 0.2.8, so this limit is not new, but it was not re-measured on 0.2.8; the numbers and the two failure signatures are in `docs/DEPLOYMENT.md` ("Memory and very large pages"), and a limit is raised only after re-measuring that. Nothing in this layer may leave a promise rejection unhandled: the service has no `unhandledRejection` handler on purpose, so one ends the process, and the `custom` url processor handed to `postcss-url` (`absolutizeAgainst()` in `rebase.js`) must never throw or reject, because `postcss-url` wraps it in a promise it can orphan. A `$` that comes from a URL (the stylesheet's path or URL, the page's path) is written as `%24` before it reaches `postcss-url` (`literalDollars()`): its replacement text is a `String#replace` template in which `$'` and `$&` sequences multiply the result. `clean-css` runs with `inline: false`, or it would read a local `@import` from the working directory. The error codes (`FETCH_ERROR_CODES`, `LOAD_ERROR_CODES`) are stable strings that tests, logs and `docs/DEPLOYMENT.md` quote, and page-controlled text in a message or a log line is cut and passed through `logSafe()`. `generateCriticalCss()` throws without the guarded browser's launcher (a Chrome that penthouse starts itself has no proxy, JavaScript-off or request-guard switches): keep that fail-closed. `critical` was removed on purpose, and `got`, `oust` and `cheerio` with it: its own HTTP client needed the SSRF policy bolted on through hooks, and its tree carried an advisory with no fixed version (GHSA-vfj7-8cjw-p6xm in `braces`, never called by this service) that kept the required audit check red; `critical` 9.x is a rewrite without penthouse/Puppeteer, so it was never an upgrade path. Do not add it back: extend the thin layer and its parity fixtures (`service/fixtures/parity/README.md`: recorded by a tool or written as a deviation, never typed by hand).
- Page JavaScript must stay OFF while Chrome renders (penthouse's own default: `blockJSRequests: true` -> `page.setJavaScriptEnabled(false)`). `server.js` passes `blockJSRequests: false` so that ONE handler owns interception, which silently drops that half; #17 did exactly that and it went unnoticed from v0.2.0 until `setupSsrfSafeRequestInterception()` (`service/ssrf-chromium.js`) started re-applying it. `page.setJavaScriptEnabled(false)` alone does NOT reach cross-site `<iframe>`/`<object>` frames (out-of-process; measured: scripts in them ran), so the browser is also launched with `JS_OFF_LAUNCH_ARGS` (`--blink-settings=scriptEnabled=false`): keep both. `ssrf-chromium.test.js` (fake page and fake browser, order-sensitive) and `service/scripts/check-js-off.mjs` in `ci.yml` (real browser: first page, `newPage()` page, a cross-site frame, plus a control that must run scripts) fail if it stops. Everything a hostile page can do beyond markup - popups, workers, WebSocket, WebRTC, WebTransport, `fetch()` - needs JavaScript, so never re-enable it to "fix" a rendering difference without a fresh SSRF review (the interception layer alone is known not to cover DNS rebinding, `*.localhost` names and `preconnect`).
- A page reaches the browser's SSRF guard through three overlapping paths (the pages that already exist, `browser.newPage()`, `'targetcreated'`; all in `guardBrowser()`), and every one of them must wait for the SAME in-flight setup: `setupSsrfSafeRequestInterception()` memoises its promise per page. A caller that only checked "already guarded" and returned handed penthouse a half-configured page: `newPage()` returned before the request handler existed (measured: the listener appeared about 300 ms later), and once JS-off was added to the setup the pages with images in a test harness hung until penthouse's 60 s timeout (that hang is timing-dependent; another reviewer could not reproduce it on an emulated arm64 host, the race itself reproduces every time). Never go back to a set-membership guard, and when a render hangs only with a new CDP call in the setup, suspect that window first.
- Chrome's ONLY way onto the network is the local policy proxy (`service/ssrf-proxy.js`); the switches that make it so are `chromeProxyArgs()`, spread into `PUPPETEER_LAUNCH_ARGS`. Never launch Chrome another way, add a launch option that opens a second path (any bypass list other than `<-loopback>`, a `direct://` fallback, `--host-resolver-rules` without `EXCLUDE 127.0.0.1`), or "simplify" the list: `--proxy-bypass-list=<-loopback>` and `--webrtc-ip-handling-policy` are each load-bearing (measured: dropping either lets a page reach a loopback listener), `--disable-quic` is only hygiene. A switch Chrome does not know is a silent no-op (`--force-webrtc-ip-handling-policy` was one) - check the binary or the behaviour, not the name. `service/scripts/check-chrome-egress.mjs` (CI) is the behavioural proof, with a control run that must reach the listeners; a Chrome bump that turns it red is a finding, not flakiness. The proxy must never throw out of an event handler (a hostile upstream's `HTTP/1.1 000` once could crash the process) - new handlers go inside `handleRequest`/`handleConnect` or get their own try/catch.
- In test and source files write bidirectional, invisible and separator characters as numeric code points (`String.fromCodePoint(0x202e)`), never literally: a raw one is a hidden-Unicode hazard in the file itself, and the editing tools have silently turned a typed `\uXXXX` escape into the real character before, which broke a regex literal.
- A cached Docker layer never sees a newer apt package: the Dockerfile's `apt-get ... --only-upgrade` layer has constant text, so with `cache-from: type=gha` v0.2.7 shipped `libexpat1` `deb12u3` although `deb12u4` was out. `publish-container.yml` therefore passes `APT_REFRESH=${{ github.run_id }}-${{ github.run_attempt }}` to BOTH its scan build and its push build (identical, so the second is answered from the first's layers on the job's one buildx builder; neither build uses the GHA cache any more - the value is new on every run, so nothing would ever read it back), the Dockerfile declares `ARG APT_REFRESH` (no default, inside the stage, right above that `RUN`), and a step fails the run if the value did not reach the layer. BuildKit says nothing about a build-arg the Dockerfile doesn't consume, so never rename, move or remove either side alone; `ci.yml` deliberately doesn't pass it. A local `docker build` that must show today's Debian needs `--no-cache` or its own `--build-arg APT_REFRESH=$(date +%s)`; a local Trivy needs a fresh DB, or it reports 0 and hides the problem.
- Chrome is pinned in `service/Dockerfile` (`ENV PUPPETEER_CHROME_VERSION`, alone on its own line) to Chrome for Testing's Stable channel, not left to puppeteer's own pin: puppeteer 25.x trails Stable's security fixes (25.12.0 pins 154.0.8037.57, which was Stable at its release; six days later Stable was 154.0.8037.92, 32 security fixes ahead per Chrome's release notes), the service executes page JavaScript with `--no-sandbox`, and Trivy, `npm audit` and Dependabot cannot see the browser. Dependabot cannot see the pin either, so `chrome-freshness.yml` (daily; an upstream outage only warns, an API that changed shape fails) fails when a Stable build newer than the pin has been out for more than 7 days: bump that one line by hand, let CI build and render with it, release - a fix only reaches users with a release. `puppeteer`'s `install.mjs` exits 0 when its download FAILS, so the checks after it in the Dockerfile are load-bearing (the newest Chrome in the cache must equal the pin - which also fails a base-image bump that ships a *newer* Chrome than the pin: bump or drop the pin, never ship the older one - and the pinned binary must report that version), and `ci.yml` asserts the pinned build is the one that launches. The Chrome download has no checksum (Chrome for Testing publishes none), where before the executed Chrome was the base image's digest-pinned copy. Builds now need egress to Chrome for Testing's storage and fail on a transient download error (re-run; every publish downloads Chrome again, after the tag exists). Dropping the pin once puppeteer's own Chrome has caught up means removing, together: the two `PUPPETEER_*` ENV lines' pin and the RUN checks that reference it, the `ci.yml` launch-assertion step, `chrome-freshness.yml`, `scripts/check-chrome-freshness.sh`, and the docs rows that describe them. The check's limits: a PERSISTENT upstream outage only warns (read the annotations), a Chrome-for-Testing JSON that stalls for days while chromiumdash lists newer builds stays green (only CfT-hosted builds can be pinned anyway), and nothing reminds you to RELEASE after a bump merges. linux/amd64 only, like the published image.
